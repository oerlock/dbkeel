# 设计文档约定

## 组织方式

- `docs/zh-CN/designs/overview.md`：整体设计，说明职责边界、公共接口和主要约束，按实际设计需要创建。
- 初期将相关设计集中在总览中；主题复杂到需要独立阅读和维护时，再拆为主题文档，并从总览链接。
- 按库的职责组织。

## 内容要求

- 文档深度与改动复杂度匹配，参考 [设计模板](./template.md)，按需删减章节。
- 明确目标与非目标，区分库负责的行为、驱动负责的差异和调用方的责任。
- 优先描述与本次主题相关的可验证契约，如输入输出、资源归属、生命周期、并发限制和失败处理，不要求逐项覆盖。
- 先明确使用场景、调用方式和必要行为；类、数据结构及继承关系按需设计，可通过最小实现验证后再确定。
- 核心接口说明通用保证；涉及数据库或底层驱动差异时，明确适用对象、能力限制和不支持时的行为。
- 流程图按需使用，保持精简；表结构和 SQL 只在设计确实涉及持久化数据时补充，例如迁移版本记录。
- 明确文档状态（草案、已采纳或已实现），标出尚未确定的问题。采纳方案不代表实现已完成；代码落地后核对并更新状态。

## 维护与决策

- 正文保持当前有效方案的完整表述，修改时整合相关内容，不逐条堆叠补丁或保留互相矛盾的结论。
- 重要取舍在相关设计中简述选择理由和放弃的方案；影响兼容性时说明升级与恢复方式。
- 普通实现变更和验证记录使用 Git 与 PR。
- 有特殊验证难点时，在设计中说明验证方式；常规测试计划与结果放在任务或 PR 中，历史测试结果不能代替当前验证。
